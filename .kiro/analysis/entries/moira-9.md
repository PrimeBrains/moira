## 2. 事象　`inferred`（素材は `derived`）

- **Given**: 予定表（ガント）の一覧ペインの「開始」「終了」列は、葉ノードで**生きた予測を主**に出し、
  基準線をフォールバックとして扱っていた（issue #34 で導入された仕様）。
- **When**: 基準線（委任時に凍結した予定）を正として運用しているチームが、朝会・進捗報告で一覧列を読む。
- **Then**: 一覧の日付が予測に流れ、委任時に凍結した日付と食い違って見える。
- **期待値**: 委任済みの基準完了日（issue 記載の例で **7/22**）。
- **実際値**: 平準化の並び順で後ろへ流れた予測日（同例で **10/26**）——後続を持たず担当者が律速資源である
  小規模タスクは、並び順ルール（トポロジ → クリティカルパス長降順 → id 昇順）でキュー最後尾に落ちるため。

出典: issue #9 本文「何が困るか（実運用の例）」。

## 3. 障害判定　`inferred` → HX 確定

**非障害** — 根拠: 当時の挙動は**明示的に決められた仕様どおり**であり（issue #34 で予測優先を採用・
その射影規則は D-76 が所有）、「意図した仕様から外れた状態」は実在しない。issue 自身も
「『予測を使う』の意図自体は理解できる」と述べ、**選択肢の追加**を求めている。

**境界事例としての読みと、それでも非障害とした理由**（steering §2「境界事例は障害側に倒す」の適用検討）:
issue は「詳細パネル側では基準と予測を並置しているのに、一覧列は予測のみ＝**呼び分け意図が食い違っている**」
とも述べており、これを「内部不整合＝仕様違反」と読む余地はある。しかし、詳細パネルの並置と一覧列の
単一表示はいずれも当時の設計として意図されたものであり（D-76 は「基準側の開始日は正典に存在しないため
近似のまま表示層に留める」と定めるにとどまり、**どちらを主に見せるかには沈黙していた**——この沈黙を
埋めたのが本 issue で起票された D-81）、**約束されたふるまいから外れた状態**とは言えない。
よって非障害。**この判定は HX で人間が確定した**（覆した履歴なし）。

## 6. 発生原因サマリ（専門用語なし）　`inferred`

**一覧に出る日付を「これから終わりそうな日」にするか「約束した日」にするかは、チームの使い方によって
答えが変わる**——ところが最初の設計では前者だけを選び、後者で運用するチームがいることが想定に入っていなかった。
そのため、約束した日を見たい人には一覧の数字が別物に見えていた。

## 7. 発生原因詳細（技術者向け）　`inferred`（素材は `derived`）

`gantt-geometry.ts` の `plannedStart`／`plannedEnd` は葉で `predicted ?? frozenSlot`（近似は
`frozenSlot − nominalDuration`）の順に解決し、親は子孫の min/max ロールアップ。
平準化器の並び順（`leveler.ts`: トポロジ → クリティカルパス長降順 → id 昇順）により、**後続を持たず
担当者が律速資源**である葉は常にキュー最後尾へ落ち、`predictedStart/Completion` が担当者の他タスクを
詰め終えた後の日付になる。表示層は単一ソースしか持たなかったため、この差は詳細パネル（基準／予測の並置）
でしか読めなかった。
出典: issue #9 本文の該当実装引用（`gantt-geometry.ts` 該当箇所・`ScheduleGantt.tsx` の列見出しと値バインド）。

## 8. 根本要因　`inferred` → HX 確定

- **仕組み帰責（必須で一度は問う）**: **設計判断の様式に「この既定は誰の運用を前提にしているか／別の運用では
  主従が逆転しないか」を問う欄・工程がない。** D-76 は「基準側の開始日は正典に存在しない」という
  *データ側の制約*までは記録したが、そこから派生する *表示上の主従*という論点には沈黙した——そして
  沈黙は起票時に検出されなかった。目録の様式（「どんな場面の話か」「他にありえた選び方」「外すとどうなるか」）は
  **選ばれた案の妥当性**は問うが、**その案が前提している利用者像**を明示的には問わない。
  結果、単一の運用モード（「早く終わりそうな順に見たい」）を暗黙の前提として既定が固まった。
- **根本要因分類**: `assumption-error`（「自明」「不要」と前提誤認した結果——ここでは「主表示は 1 つで足りる」）
- **詳細**: 当時の判断は「早く終わりそうな順に見える」というソート用途の要請から出発しており、その用途では
  予測を主にするのが自然だった。前提が誤っていたのではなく、**前提が 1 つしか置かれていなかった**。
  基準線を正として運用するチームの存在は、実運用で当事者が声を上げるまで設計に入らなかった。
