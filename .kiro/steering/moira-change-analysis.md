# Moira 要因分析フロー（受付・振り分け → 記入 → 人間確認 → 横断集約 → 是正 Try）

本ファイルは、**変更管理フロー**（[moira-change-management.md](moira-change-management.md)）が
**変更を通す**工程列であるのに対し、**通り終えた変更を振り返る**工程列の規範である。前者の出口（P6 クローズ）が
後者の入口になる。既存ゲート・既存の委譲辺は**変更しない**——本フローは検証器ではなく事後分析である。

**状態**: 2026-07-25 人間承認（issue #19・DFD v3 承認）。**本文書自体の以後の改訂は変更管理フローを通す**。
**来歴**: `moira/plans/2026-07-25-change-analysis-dfd.md`（DFD 3 枚・既存フローの現況監査・裁定記録）が保持する。
**設計判断**: `moira/DECISIONS-CATALOG.md` D-82〜D-86（＋キー修飾は D-80 の適用）。

## 0. 一文の定義とスコープ

**要因分析フローとは、クローズ済みの変更 1 件（GitHub issue ＋ `moira/changes/issue-N/` 台帳 ＋ 実差分）を単位に、
まず「障害か非障害か」を受付で振り分け、障害は不具合台帳へ・非障害は変更分析台帳へ——どちらも共通の項目定義と
タクソノミーで——分析票を起こし、「①履歴からの導出／②AI 推論／③フロー実行時の採取」の三系統で、埋められない欄は
埋められないと記録したまま埋め、同件を横断集約して、仕組み（skill・steering）側の是正 Try に落とす工程列である。**

### スコープの正直な宣言（先に限界を書く）

1. **全項目の自動充填は成立しない。** 17 項目のうち **7 項目は既存の入力にそもそも存在しない**（障害判定・変更分類・
   根本要因・再発防止策・検知すべき工程・検知できなかった理由・検知対策。issue #19 の実地監査）。本フローは
   **AI 推論＋人間確認**で埋め、**各欄に出所ラベルを必須**とする（§4）。「履歴を読めば全部わかる」とは主張しない。
2. **本フローは検証器（計器）ではない。** 事後分析であり、変更を止める権限も合否も持たない。
   計器①〜⑥（[moira-verification.md](moira-verification.md)）にも変更管理フローのゲート群にも**加わらない**。
3. **過去分は「当時の判断の記録」ではなく「事後の再構成」である。** クローズ済み issue の障害判定・検知工程は
   当時どこにも記録されていない——起こすのは後知恵の再構成であり、台帳はそれを `inferred` ラベルで明示する。
4. **同件調査の網羅性は保証しない。** 台帳の見出しには表記ゆれが実在し、抽出は regex ではなく意味検索に依る。
   見落としは残る（`decision-conformance` の意味突合と同じ正直枠）。
5. **「定期的」を外部スケジューラで強制はしない。** 起動トリガの**規約**を定義するところまでが本フローで、
   cron 等の配線は含めない（§6）。
6. **強制機構ではない。** 変更管理フロー（§0）と同じ紳士協定であり、記録漏れを機械的に防ぐ機構ではない。

## 1. 全体の工程

| 工程 | in | 処理 | out |
|---|---|---|---|
| **A0 受付・振り分け** | §6 の 5 トリガ／GitHub issues／`moira/changes/issue-*/`／両台帳の index | ①母集団を repo 修飾キーで列挙し、両台帳に entry の無いものを未分析キューへ（**キューは保存せず毎回算出**）②**障害／非障害を判定**（AI ドラフト → HX で人間確定）③振り分け | 未分析キュー＋**振り分け判定（判定・根拠・出所ラベル）** |
| **A1 証跡収集** | キー 1 件 | issue 本文・**全コメント**（triage／HA／閉包サマリはここにある）・台帳 5 種＋補助 md（`gate-round-records.md` 等）・`git diff --name-only`・関連する既存 entry を集める | 証跡束（各断片に**出典パス／URL**） |
| **A2 導出** | 証跡束 | 履歴に**在る**項目を写す（§3 の `derived` 欄） | 一次記入票 |
| **A3 推論** | 一次記入票＋証跡束 | 履歴に**在らざる**項目を埋める。**根拠を示せない欄は `unknown`（捏造禁止）** | 分析票ドラフト |
| **HX 人間確認** | 分析票ドラフト | 人間が読むのは **4 群だけ**——①障害判定 ②根本要因（仕組み帰責）③再発防止策 ④検知対策。他は読む義務なし | 批准済み entry |
| **A4 記録** | 批准済み entry | **障害** → `/kiro-postmortem-add` へ委譲（`.kiro/postmortem/defects.md`）／**非障害** → `.kiro/analysis/entries/<repo>-<番号>.md`＋`INDEX.md` | 台帳 entry |
| **A5 横断集約** | **両台帳**の全 entry | 4 軸（変更分類 × 根本要因 × 対象システム × 検知工程ギャップ）の頻度と同件クラスタ → Try 候補 | `.kiro/analysis/reviews/<日付>.md` |
| **HY Try 裁定** | Try 候補 | 人間が採否を裁定。採用分は**既存の出口**へ（`/kiro-steering-custom` ／ issue 起票 → `moira-change`）——**本フローは自分で確定文書を書き換えない** | 反映済み Try |

**人間タッチポイントは 2 点のみ**（HX・HY）。**新造ゲートを作らない**——本フローは合否判定器を持たない。

## 2. A0 の判定基準（障害／非障害）

| 判定 | 定義 |
|---|---|
| **障害** | 意図した仕様・約束されたふるまいから外れた状態が**実在した**変更（バグ FIX・欠陥是正・回帰）。**潜在（未発現）欠陥も障害に含める**——観測者がいなくても仕様違反状態は実在した |
| **非障害** | 要件追加・要件変更・リファクタリング・テスト追加・運用変更・仕組み改善・文書のみ |

- **境界事例は `障害` 側に倒し、理由を記録する**（見落としより過剰記録を選ぶ）。
- **判定を覆した履歴も残す**（entry 内に記録。振り分けの監査可能性が本工程の存在理由である）。
- 判定と根拠は**必ず記録される**——暗黙の振り分け（記録しないことで非障害扱いにする）を禁じる。

### 2.1 入口フィルタ——「すり抜けギャップ」基準（D-84）

**検出の主体（誰が見つけたか）では線を引かない。** 判定式は次の一本である。

> **「検知すべき工程」≠「実際に検知した工程」**（＝本来捕まえるべき工程より下流で見つかった）**なら入口へ。
> 等しければ入口にしない。**

これは §3 の項目 13/14 そのものであり、**新しい判定基準を発明しない**。

| 事象 | 入口か |
|---|---|
| 敵対ゲートのラウンド内で決着した指摘／実装中のテスト失敗／型エラー | **入口にしない**（工程が設計どおり働いた証拠） |
| P5 閉包で未マップ差分が見つかり P2 へ差し戻し | **入口にしない**（P5 は元々それを捕まえる工程） |
| クローズ済み変更の欠陥が、後の issue の影響調査・`decision-conformance` の DRIFTED・`kiro-scenario-e2e` の discrepancy で発覚 | **入口**（すり抜け） |
| deferred Important ／ `[intent-drift]` ／ `[rdt-disposal]` の実害化 | **入口**（撤回条件タグはこれを数えるために在る） |
| main マージ後の CI 赤・運用中の発覚 | **入口**（`post-close`） |

**どの入口でも AI はキューに積むだけ**で、都度「起票しますか」と問わない（起動は §6 に従う）。

## 3. 分析票の項目（17 項目・障害／非障害で共通）

| # | 項目 | 既定の充填系統 | 語彙／様式 |
|---|---|---|---|
| 1 | 対象システム | derived | `backend` / `frontend` / `cli` / `adapter` / `process`（skill・steering・確定文書・台帳）。複数可 |
| 2 | 事象 | inferred | Given / When / Then ＋**期待値／実際値**。非障害では「Then＝変更後にこうなる」 |
| 3 | 障害判定 | **A0 で判定 → HX で人間確定** | `障害` / `非障害`＋根拠（§2） |
| 4 | 変更分類 | inferred | `req-change` / `req-add` / `refactor` / `bugfix` / `test-add` / `ops-change` / `process-improve` / `doc-only` / `other` |
| 5 | 変更範囲 | derived | 影響マップのクラス列＝ **M/D/P/S/C/V/F の 7 値**（変更管理 §3 の既存語彙。競合語彙を新設しない） |
| 6 | 発生原因サマリ | inferred | **専門用語なし**の平易文 1〜2 文 |
| 7 | 発生原因詳細 | inferred | 技術者向け・出典パス付き |
| 8 | 根本要因 | inferred → **HX 確定** | **仕組み帰責を必ず一度は問う**（SKILL／steering／テンプレート／工程配線／タクソノミー／人間タッチポイント設計に穴がなかったか）＋根本要因分類ラベル 1 つ。**該当時は literal タグ `[deferred-important]`／`[rdt-disposal]`／`[intent-drift]` を本文に含める**（他機構の撤回条件が grep で数える計器） |
| 9 | 同件調査対象 | derived | 走査した母集団の明示。**範囲を書かない「該当なし」を認めない** |
| 10 | 同件調査結果 | inferred | 有無＋該当キー。**網羅性は保証しない** |
| 11 | 同件の対応状況 | derived | 別 issue のキー＋リンク＋state（`gh issue view` で機械照合） |
| 12 | 再発防止策 | inferred → **HX 確定** | **出口を名指す**（steering／skill／テンプレート／計器） |
| 13 | 検知すべき工程 | inferred | §5 のタクソノミー |
| 14 | 実際に検知した工程 | derived（`gate-round-records.md` 等）／無ければ inferred | §5 のタクソノミー |
| 15 | なぜ然るべき工程で検知できなかったか | inferred → **HX 確定** | 13≠14 なら必須。13=14 なら「同工程で検知」 |
| 16 | 検知するための対策 | inferred → **HX 確定** | 計器・ゲート・チェックリストのどれを足すか名指す |

**メタ欄**: `key`（repo 修飾）／`Schema`（`v1`＝旧 10 項目／`v2`＝本 17 項目）／`analyzed-at`／
`status`（`drafted` → `ratified` → `aggregated`）／`sources`／各欄の出所ラベル。

## 4. 出所ラベル（正直枠の中核・D-83）

| ラベル | 意味 |
|---|---|
| `derived` | 履歴（issue・台帳・git）から写した。**出典パス／URL 必須** |
| `inferred` | AI が推論した。**根拠（どの記述から）必須**・後知恵の再構成であることを含意 |
| `captured` | 変更管理フローの実行時に採取された一次記録（§7 の 2 欄のみ） |
| `unknown` | 埋められない。**空欄・推測での穴埋めを禁じる**——「わからない」を記録する |

## 5. タクソノミー（正本は 1 ファイル・D-82）

**正本は `.claude/skills/kiro-postmortem-add/rules/taxonomy-reference.md`**。
`.kiro/postmortem/defects.md` ヘッダは**要約＋正本へのポインタ**であり、定義の正本ではない
（複数ファイルを同期義務で結ぶ形は「正本 1 つ」ではない）。

| 軸 | 扱い |
|---|---|
| 要因分類（What） | 既存を再利用 |
| 根本要因分類（Why） | 既存を再利用（項目 8 の「仕組み帰責」は散文で補う） |
| 発生機能 | **対象システム 5 値**（`backend`/`frontend`/`cli`/`adapter`/`process`）＋自由サブスコープ |
| 検知工程（Where） | V モデル軸＋**プロセス軸**（下記）を併存 |
| 変更分類 | §3 #4 の 9 値 |

**検知工程のプロセス軸**: `p1-triage`（受付・triage）／`p2-impact-survey`（影響調査）／
`ha-ratification`（HA 前半集約セッション）／`gate-adversary`（各ゲートの敵対レビュー）／
`gate-judge`（独立採点・独立照合）／`p5-closure`（同期閉包確認）／`ci`（計器①②③④）／
`post-close`（クローズ後の発覚＝全工程をすり抜けた状態）。

## 6. 起動トリガ（D-85）

**既定は手動起動＋AI からの 1 行提案。AI はユーザー確認なしに分析を起動しない。**

| ID | トリガ | 検出契機 |
|---|---|---|
| (a) | `queue-threshold` | 未分析キューが **10 件**以上 |
| (b) | `periodic` | 前回分析から **1 か月**経過 |
| (c) | `post-close` | `moira-change` P6 クローズ直後——**キューに積むだけ**（クローズを重くしない） |
| (d) | `escaped-defect` | §2.1 のフィルタを通った欠陥——**即時にキューへ積むだけ** |
| (e) | `user-explicit` | ユーザー明示（常時許容・AI 提案不要） |

**未分析キューは保存しない**——「クローズ済み issue − 両台帳に entry のあるキー」で毎回算出する
（保存すると台帳と現実がずれた瞬間に嘘をつく）。**外部スケジューラは配線しない**。

## 7. 変更管理フロー実行時の一次採取（2 欄のみ・D-83）

`moira-change` の **P6 クローズ時**に、閉包レポート（および issue クローズコメント）へ次の 2 欄だけを記録する:

1. **障害判定**（`障害` / `非障害`＋一言の根拠）
2. **変更分類**（§3 #4 の 9 値から 1 つ）

**それ以外は採取しない**——検知工程・根本要因まで実行時に書かせるとクローズ工程が重くなり、
ratified 文書の改訂範囲も大きくなる。過去分は採取不能なので、いずれにせよ推論経路（§4 `inferred`）は必須である。

## 8. 母集団とキー規約

- **キー**: `<repo>#<number>`（例 `moira#16`）。**無修飾の `#N` を禁じる**——`moira/changes/issue-39/42/43` は
  旧リポ `PrimeBrains/sdd-workshop` の番号であり本リポの同番号と衝突する。**これは D-80 の適用**であり、
  D-80 の「本文は書き換えない」に従って**既存文書の `#N` を遡及修飾しない**（修飾義務は本台帳が新規に書くキーのみ）。
- **母集団**: 本リポ（`PrimeBrains/moira`）のクローズ済み issue ＋ 対応する `moira/changes/issue-N/`。
  台帳のない軽量 exit の issue も**対象に含む**（多くの欄が `inferred`／`unknown` になる）。
- **旧リポ由来**: 既定で対象外（移管前・別プロセス）。明示指定時のみ分析する。

| **障害**の分析票 | `.kiro/postmortem/defects.md`（`/kiro-postmortem-add` が append） |
| **非障害**の分析票 | `.kiro/analysis/entries/<repo>-<番号>.md`（1 件 1 ファイル） |
| 分析済み一覧・状態 | `.kiro/analysis/INDEX.md` |
| 横断集約の結果と Try 裁定 | `.kiro/analysis/reviews/<日付>.md` |
| Try の steering 反映ログ | `.kiro/postmortem/defects.md` の `## Steering 反映ログ`（既存の場所を維持） |

既存の分担に従うため（`.kiro/postmortem/`・`.kiro/steering/`・`.kiro/scenarios/` と同列）。

## 10. 既存の不具合振り返り機構との関係（D-86）

- **依存方向は一方向**: 本フロー（`moira-change-analysis`）→ `/kiro-postmortem-add`（障害 entry の記録を委譲）。
  逆向きの依存を作らない。
- **既存機構の改訂は「死んだ配線の是正」に限る**。**思想は変えない**——記録 → 集約 → 反映の 4 段構成、
  記録の 3 状態（`recorded`/`reviewed`/`steered`）、追記のみの規律、全項目が埋まるまで追記しない規律、
  `.kiro/steering/` は `/kiro-steering-custom` 経由でのみ触る規律、人間確認なしに追記・起動しない規律。
- **過去の記録は遡って書き換えない**。読み取り側は **`Schema: v1`（10 項目）と `v2`（17 項目）の 2 様式を受理**し、
  **v1 entry を malformed として集計から外さない**（欠落項目は `unknown` として数える）。`Schema:` を持たない
  既存 entry は **v1 とみなす**。

## 11. 本フローが**しないこと**（過大主張の禁止）

- 変更を止めない・合否を出さない（検証器ではない）。
- 全項目を自動で埋めない（§0-1）。
- 確定文書を自分で書き換えない（Try は既存の出口へ渡す）。
- 網羅的な同件検出を保証しない（§0-4）。
- 既存 PDCA 思想を作り替えない（§10）。
- 記録漏れを機械的に防がない（§0-6。漏れは後日 issue として再入させる）。

## 12. 実装形態

- **skill**: `.claude/skills/moira-change-analysis/`（`SKILL.md`／`SKILL.ja.md`＋`templates/`）——A0・A1〜A3・A4（非障害）・
  A5 の振り付けを所有し、規範（本ファイル）を複製しない。障害 entry の記録は `/kiro-postmortem-add` へ委譲。
- **既存 skill**: `/kiro-postmortem-add`・`/kiro-postmortem-review` に §10 の是正を適用（`SKILL.md`／`SKILL.ja.md` の
  **両方**——両者は並行翻訳であり、片方だけの是正は不整合を残す）。
- **コードは書かない**——台帳の見出しには表記ゆれが実在し、抽出は regex ではなく AI の意味読解に依る。
  列挙は `gh`・`git`・`ls` で足りる。
