## 入口種別

issue直

## 明確化した変更要求文

**GitHub issue と `moira/changes/issue-N/` 配下に蓄積された「変更管理の履歴」を入力として、
定期的に要因分析（変更 1 件ごとの事象・原因・再発防止の構造化分析）を行う仕組みを新設する。**

要求の内訳（issue 本文の書き起こし）:

1. **入力**: (a) GitHub issue（本文・コメント・クローズ時サマリ）と (b) リポジトリ内の
   `moira/changes/issue-N/`（変更管理フローの作業台帳: request / impact-map /
   intent-ratification / fork-batch / closure-report）。この 2 系統に既に保存されている情報を
   分析の素材とする。
2. **周期性**: 「定期的に」実施できること——単発の分析ではなく、繰り返し起動され、
   前回分析済みの範囲との差分を扱える運用形態であること（起動トリガの具体は設計事項）。
3. **成果物**: 下記 16 項目を持つ要因分析結果。
4. **手順の順序拘束（人間からの明示指示）**: **まず DFD（データフロー図＝仕組みの工程間配線図）を
   作成し、人間の承認を得てから実装に移る**こと。DFD 未承認のまま実装成果物を作らない。

### 明確化にあたって解いた曖昧さ（原文は issue に残る・情報は失わない）

- 「要因分析」の対象単位 = **変更 1 件**（= issue 1 本）と読む。項目 3「障害判定（障害／非障害）」が
  あることから、対象は不具合に限らず**全ての変更**（要件追加・リファクタリング等を含む）である。
- 「変更範囲（S/P/D/C）」は本リポジトリの変更クラス分類（steering §3 の M/D/P/S/C/V/F）と
  同じ語彙だが**部分集合**になっている。意図（略記か、意図的な 4 値への絞りか）は P3 の HA 境界裁定へ送る。
- 「仕組みをつくる」の成果物形態（skill か CLI か文書か、その組み合わせか）は指定されていない。
  DFD で提示して承認を得る。

## 候補クラス（仮判定）

| クラス | 該当 | 根拠 |
|---|---|---|
| M（MODEL・正典設計物級） | 未定（P2 で確定） | 本件は Moira 製品の公理・語彙・イベント意味論ではなく**プロセス側の機構**。ただし新設物が `moira-model-update` 所有の確定設計物（NAMING・moira 系 agent 定義）に触れる場合のみ M。現時点では該当なしと見る |
| D（設計判断級） | Y | 0→1 の構造判断が複数ある: ①分析結果の**置き場と所有権**（`.kiro/postmortem/defects.md` の拡張か、独立台帳か）②既存 postmortem 機構（`/kiro-postmortem-add` / `/kiro-postmortem-review`）との**境界・依存方向** ③16 項目のうち履歴から**導出できない項目の扱い**（新規採取か AI 推論か非適用か）④「定期的」の起動トリガの所在。MODEL は本論点に沈黙（＝拡張） |
| P（プロパティ級） | 未定（P2 で確定） | 現時点で不変条件の新設・改訂は見えない。分析機構が Moira の不変条件に触れないなら該当なし |
| S（シナリオ級） | 未定（P2 で確定） | 本機構は Moira 製品（backend/frontend/cli）の観測ふるまいではなくプロセス機構のため、`.kiro/scenarios/` の unit には原則載らないと見る。CLI 実装形態を採る場合のみ再検討 |
| C（コード級） | 未定（P2 で確定） | 実装形態が skill＋文書で閉じるならなし。集計・抽出を CLI/スクリプトで持つ設計を採る場合は該当 |
| V（検証基盤級） | 未定（P2 で確定） | 検知器（CI・coverage-check 等）そのものは変更しない見込み |
| F（一般確定文書級） | Y | 確実に該当: ①新設 skill 定義（`.claude/skills/*/SKILL.md`・`SKILL.ja.md`）②DFD 設計文書（`moira/plans/`）③分析結果台帳の README／様式規約。**さらに `.kiro/steering/moira-change-management.md` 自体の改訂**（分析に必要な情報をフロー実行時に採取する必要が判明した場合。同文書は「以後の改訂は本フローを通す」と自ら宣言しており、本フロー内で扱えば規律に適合） |

**仮の主クラス**: **D＋F**（設計判断を doc-refine で確定し、確定文書群を doc-refine で確定する）。
C/S/P/V は P2 の調査結果で確定する。境界不明瞭な部分は steering §3 の既定ルート（D 級起票）に従う。
